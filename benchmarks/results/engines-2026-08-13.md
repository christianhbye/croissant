# Engine benchmark conclusions (2026-08-13)

All 30 configurations agree with `s2fft` to at most 2.6e-14 relative
(worst case: spin=0, nside=16, niter=0/3, dense), far inside the ~1e-10
bar, so none of the timing differences below are a speed/accuracy
trade-off — see the raw output and table below for every value.

## 1. Amortisation threshold (kernel setup+first vs s2fft)

This benchmark uses a fixed batch of 4 leading (frequency) elements in
every configuration (`data.shape == (4, npix)`); batch size itself is
not swept, so the crossover cannot be read off as an exact number, only
bounded at this one point. At batch=4, `kernel` setup+first already
beats `s2fft` setup+first in 9 of the 10 spin/nside/niter combinations,
by 1.5x-4.6x. The lone exception is spin=+0, nside=32, niter=0, where
`kernel` (2.853 s) is about 8% *slower* than `s2fft` (2.640 s) -- a
near-tie, not a clear loss. Since a threshold of 4 already wins almost
everywhere and only barely loses in one unrefined, largest-nside cell,
the data supports lowering `_AMORTISATION_THRESHOLD` from the plan's
placeholder of 8 to 4, rather than confirming 8. Re-run with a real
batch-size sweep before finalizing Task 7 if a tighter number is wanted;
this benchmark only establishes an upper bound of "4 is enough" almost
everywhere, not the true crossover.

## 2. kernel vs dense cached-apply at niter=3

`dense` wins outright, in every one of the 5 tested spin/nside pairs,
by 1.6x-3.4x:

| spin | nside | kernel cached (s) | dense cached (s) | dense speedup |
|---:|---:|---:|---:|---:|
| +0 | 8 | 0.002407 | 0.000774 | 3.11x |
| +0 | 16 | 0.004472 | 0.002837 | 1.58x |
| +0 | 32 | 0.049377 | 0.029601 | 1.67x |
| +2 | 8 | 0.002321 | 0.001135 | 2.05x |
| +2 | 16 | 0.013466 | 0.003924 | 3.43x |

This directly contradicts the FLOP argument in the plan (kernel should
win per call for any nside > 4): a dense matmul is one BLAS call with
ideal arithmetic intensity, while the kernel path pays `2*niter+1 = 7`
sequential FFT+einsum round trips at niter=3, and that access-pattern
cost dominates the smaller operand size. **Task 7 should reinstate the
`niter > 0 and dense_fits -> dense` branch**, citing this table. For
context, at niter=0 the ranking mostly reverses (kernel beats or ties
dense in 4 of 5 pairs; see the full table below) -- it is specifically
the refinement round trips that flip the result.

## 3. kernel-vs-dense setup and memory ratios

Memory (dense_mib / kernel_mib, reality flag matched to what the field
actually uses): scalar (reality=True) 6.9x / 12.8x / 24.8x at
nside=8/16/32; spin (reality=False, forced for spin!=0) 12.8x / 24.6x
at nside=8/16. Both grow roughly linearly with nside, as the plan's
`~1.5*nside` argument predicts directionally, but the plan's Background
section quotes ~24.7x at nside=16 and ~48.8x at nside=32 -- almost
exactly double what is measured here. That is because the old figures
paired a `reality=False` dense footprint (confirmed: `dense_nbytes(...,
reality=False)` gives exactly 48.0 MiB at nside=16 and 768.0 MiB at
nside=32, matching the old table) with a `reality=True` kernel
footprint (1.94 / 15.75 MiB, also matching). The old ratio was an
apples-to-oranges comparison; with the reality flag held consistent
the true scalar ratio is about half that. **Task 8's README table
should use 6.9x / 12.8x / 24.8x (scalar) and 12.8x / 24.6x (spin), not
the old 24.7x/48.8x.**

Setup (`dense` setup+first / `kernel` setup+first): for scalar fields
the ratio is noisy and small at nside<=16 (1.42x at nside=8, niter=0;
*0.94x* at nside=16, niter=0 -- dense measured marginally faster,
fixed overhead dominates at this size), rising to 5.8x-6.8x at
nside=32. For spin fields the ratio is far larger at every tested
nside: 38.0x (nside=8, niter=0), 23.6x (nside=16, niter=0), 12.7x
(nside=8, niter=3), 30.8x (nside=16, niter=3) -- the dense engine's
numpy spin Wigner-d builder is disproportionately expensive relative to
the kernel builder, well beyond what the scalar case or the `1.5*nside`
argument would suggest. Task 8 should report the scalar and spin setup
ratios separately rather than a single number.
