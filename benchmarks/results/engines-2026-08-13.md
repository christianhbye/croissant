# Engine benchmark conclusions (2026-08-13, fix round 1)

All 30 grid configurations agree with `s2fft` to at most 1.4e-13
relative (worst case: spin=0, nside=32, dense), far inside the ~1e-10
bar, so none of the timing differences below are a speed/accuracy
trade-off.

This revision fixes two problems found in fix round 1: (1) the
reported kernel memory footprint used `kernel_nbytes(...)` without
`reality=reality`, silently defaulting to `reality=False` and reporting
a kernel twice its real size for every scalar configuration; (2) the
first run reused JAX's process-wide jit compilation cache across
configurations that happened to share a shape, which is now cleared
with `jax.clear_caches()` before every timed run (croissant's own
`clear_kernel_cache()`/`clear_dense_matrix_cache()` only clear its own
object caches, not JAX's compiled-executable cache) — this also
changed several `setup_plus_first_seconds` values from the first run,
since those measurements now genuinely pay full recompilation cost
every time rather than occasionally inheriting a warm cache.

## 1. Amortisation threshold (kernel setup+first vs s2fft)

Added a dedicated batch-size sweep at one fixed configuration (scalar,
nside=16, lmax=31, niter=0) over batch sizes 1, 2, 4, 8, 16, with
`jax.clear_caches()` before every timed call so each measurement is a
genuine cold start. Result: `kernel` wins at **every** tested batch
size, including batch=1 (kernel 1.056 s vs s2fft 1.602 s). The sweep
found no crossover in 1-16 because kernel is ahead throughout this
range — the true crossover for this configuration is at or below
batch=1.

This does not generalize across nside, and the contradiction is
visible in this benchmark's own main grid: at spin=+0, nside=32,
niter=0, batch=4 (same cache-clearing discipline), `kernel` (3.482 s)
is slower than `s2fft` (2.905 s) — kernel *loses* at batch=4 when
nside=32, while it *wins* at batch=1 when nside=16. A single global
`_AMORTISATION_THRESHOLD` batch-size cutoff, independent of nside,
cannot represent both facts correctly. Recorded recommendation: treat
`_AMORTISATION_THRESHOLD` as a coarse heuristic tuned for the common
case, not a tight bound — a value of 1-2 is what this sweep supports
at nside=16, but Task 7 should sweep nside=32 (and larger) too before
trusting a single constant near the top of the nside range this
benchmark tests.

## 2. kernel vs dense cached-apply at niter=3

`dense` wins outright, in every one of the 5 tested spin/nside pairs:

| spin | nside | kernel cached (s) | dense cached (s) | dense speedup |
|---:|---:|---:|---:|---:|
| +0 | 8 | 0.003849 | 0.000579 | 6.65x |
| +0 | 16 | 0.008349 | 0.001492 | 5.60x |
| +0 | 32 | 0.052603 | 0.024667 | 2.13x |
| +2 | 8 | 0.004440 | 0.001306 | 3.40x |
| +2 | 16 | 0.006984 | 0.005425 | 1.29x |

This directly contradicts the FLOP argument in the plan (kernel should
win per call for any nside > 4): a dense matmul is one BLAS call with
ideal arithmetic intensity, while the kernel path pays `2*niter+1 = 7`
sequential FFT+einsum round trips at niter=3, and that access-pattern
cost dominates the smaller operand size. Ruling accepted: **Task 7
reinstates the `niter > 0 and dense_fits -> dense` branch**, citing
this table; the plan's FLOP-only argument does not hold on wall-clock.

## 3. kernel-vs-dense setup and memory ratios

Memory (dense_mib / kernel_mib, both built with the `reality` flag the
engine actually uses): scalar (reality=True) **13.3x / 25.3x / 49.1x**
at nside=8/16/32; spin (reality=False, forced for spin!=0) 12.8x /
24.6x at nside=8/16. This now matches the plan Background's ~24.7x
(nside=16) and ~48.8x (nside=32) figures closely (the earlier draft of
this report had the ratio wrong by 2x and wrongly concluded the plan's
figures were the artefact — they were not; the bug was in this
benchmark's `kernel_nbytes` call omitting `reality=reality`, silently
defaulting to `reality=False` and reporting a 2x-oversized kernel for
every scalar configuration). Task 8's README table should use
13.3x/25.3x/49.1x (scalar) and 12.8x/24.6x (spin).

Setup (`dense` setup+first / `kernel` setup+first): for scalar fields
the ratio is small or even <1 at nside<=16 (1.07x at nside=8, niter=0;
*0.69x* at nside=16, niter=0 -- dense measured faster, fixed overhead
dominates at this size), rising to 4.2x-5.8x at nside=32. For spin
fields the ratio is far larger at every tested nside: 26.8x
(nside=8, niter=0), 22.2x (nside=16, niter=0), 15.5x (nside=8,
niter=3), 23.1x (nside=16, niter=3) -- the dense engine's numpy spin
Wigner-d builder is disproportionately expensive relative to the
kernel builder. Task 8 should report the scalar and spin setup ratios
separately rather than a single number.
