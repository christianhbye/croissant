# Engine benchmark conclusions (2026-08-13, fix round 2)

All 30 grid configurations agree with `s2fft` to at most 1.4e-13
relative (worst case: spin=0, nside=32, dense), far inside the ~1e-10
bar, so none of the timing differences below are a speed/accuracy
trade-off.

This revision replaces conclusion 1 only, in response to fix round 2:
the single-resolution sweep in the previous revision (nside=16 only)
showed kernel winning at every batch size 1-16, but the main grid
showed kernel *losing* to s2fft at nside=32/niter=0/batch=4 — a
contradiction a single-resolution sweep cannot resolve. The sweep now
runs at three resolutions (nside=8, 16, 32; scalar; niter=0; batch
sizes 1, 2, 4, 8, 16, 32; `jax.clear_caches()` before every timed
call). Conclusions 2 (niter=3, dense wins) and 3 (corrected memory
ratios) carry the same rulings as the previous revision; their exact
figures below are recomputed from this run's fresh main-grid numbers
(which move a little from run to run, as wall-clock benchmarks do —
see the fix-round section of the task report for the full comparison)
and repeated here for completeness.

## 1. Amortisation threshold (kernel setup+first vs s2fft)

Measured crossover batch size — the smallest tested batch at which
`kernel` setup+first first beats `s2fft` setup+first — at each
resolution:

| nside | kernel_mib | crossover batch size |
|---:|---:|---:|
| 8 | 0.12 | 1 (wins at every tested batch, 1-32) |
| 16 | 0.98 | 1 (wins at every tested batch, 1-32) |
| 32 | 7.94 | 8 (loses at 1, 2, 4; wins at 8; one noisy blip back to s2fft at 16 within 0.1% of a tie; wins clearly at 32) |

**A single global `_AMORTISATION_THRESHOLD` is not defensible.** The
crossover moves by 8x between nside=16 and nside=32 while
`kernel_mib` also grows by 8.1x over the same step (matching the
`~nside**3` scaling `kernel_nbytes` documents) — the crossover tracks
the kernel's build cost, not a fixed number of transforms. Fitting the
three points against `kernel_mib` gives crossover/kernel_mib of 8.3
(nside=8, only an upper bound since the sweep floors at batch=1 and
the true crossover there could be lower), 1.02 (nside=16, same floor
caveat), and 1.01 (nside=32, not floored). The nside=16 and nside=32
points agree with each other to within 1%: **crossover batch size ≈
kernel_mib (roughly 1 batch element needed per MiB of kernel
footprint)**. Any fixed constant that is safe at nside=32 (>= 8) is
needlessly conservative at nside=8/16 (kernel already wins there from
batch=1), and any constant aggressive enough to exploit that
(<= 2) is wrong at nside=32 and would get worse at larger nside still,
since `kernel_mib` keeps growing as `nside**3` while a fixed integer
does not. Recorded recommendation: **Task 7 should replace the fixed
`_AMORTISATION_THRESHOLD` with a comparison scaled by
`kernel_nbytes(...)`** (already computed in `resolve_engine`), using
roughly 1 MiB of kernel footprint per unit of `batch_size` as the
calibration this sweep supports, rather than a single constant. This
is only three data points, so treat the ~1:1 coefficient as an
order-of-magnitude guide to be refined, not a precise fit.

## 2. kernel vs dense cached-apply at niter=3

`dense` wins outright, in every one of the 5 tested spin/nside pairs:

| spin | nside | kernel cached (s) | dense cached (s) | dense speedup |
|---:|---:|---:|---:|---:|
| +0 | 8 | 0.004557 | 0.000547 | 8.33x |
| +0 | 16 | 0.008758 | 0.001693 | 5.17x |
| +0 | 32 | 0.052929 | 0.021933 | 2.41x |
| +2 | 8 | 0.002864 | 0.001365 | 2.10x |
| +2 | 16 | 0.013584 | 0.005266 | 2.58x |

This directly contradicts the FLOP argument in the plan (kernel should
win per call for any nside > 4): a dense matmul is one BLAS call with
ideal arithmetic intensity, while the kernel path pays `2*niter+1 = 7`
sequential FFT+einsum round trips at niter=3, and that access-pattern
cost dominates the smaller operand size. Ruling accepted: **Task 7
reinstates the `niter > 0 and dense_fits -> dense` branch**, citing
this table; the plan's FLOP-only argument does not hold on wall-clock.

## 3. kernel-vs-dense setup and memory ratios

Memory (dense_mib / kernel_mib, both built with the `reality` flag the
engine actually uses): scalar (reality=True) **13.3x / 25.3x / 49.1x**
at nside=8/16/32; spin (reality=False, forced for spin!=0) 12.8x /
24.6x at nside=8/16. This matches the plan Background's ~24.7x
(nside=16) and ~48.8x (nside=32) figures closely. Task 8's README
table should use 13.3x/25.3x/49.1x (scalar) and 12.8x/24.6x (spin).

Setup (`dense` setup+first / `kernel` setup+first, from the main
grid): for scalar fields the ratio is small at nside<=16 (1.15x at
nside=8, niter=0; 0.82x at nside=16, niter=0 -- dense measured
marginally faster, fixed overhead dominates at this size), rising to
5.9x at nside=32. For spin fields the ratio is far larger at every
tested nside: 24.9x (nside=8, niter=0), 22.5x (nside=16, niter=0),
14.7x (nside=8, niter=3), 24.8x (nside=16, niter=3) -- the dense
engine's numpy spin Wigner-d builder is disproportionately expensive
relative to the kernel builder. Task 8 should report the scalar and
spin setup ratios separately rather than a single number.
